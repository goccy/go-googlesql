# Would converting the wasm2go bodies to Plan 9 asm help?

**Yes — dramatically — and it directly attacks the root cause.** The reason
golangci-lint is slow is that `go/types` must parse and type-check ~5.3M lines of
generated Go. Plan 9 assembly (`.s`) bypasses the Go front-end entirely: the
linter (and the compiler front-end) sees only the tiny Go *stub signatures*
(`func FnN(...) int32`), never the bodies. The bodies are assembled by the
toolchain's assembler, which `go vet`/golangci do not run as part of analysis.

## Measured proof of concept

Generated two equivalent packages: 4,000 functions × 30 wasm-like ops each.
`gopkg` = ordinary Go source; `asmpkg` = Go stub declarations + an amd64 `.s`
with the same number of instructions per function. Cold cache (std pre-warmed),
measured with `runmax` (wall + peak RSS).

| package | source | `go build` wall | build RSS | **govet wall** | **govet RSS** |
|---|---|---|---|---|---|
| `gopkg` (Go source) | 376,007 lines / 7.0 MB | 9.21 s | 638 MB | **15.83 s** | **1099 MB** |
| `asmpkg` (stubs + `.s`) | 111 KB stubs + 1.8 MB `.s` | 1.14 s | 117 MB | **2.37 s** | **159 MB** |
| **ratio** | | **8.1×** | 5.4× | **6.7×** | **6.9×** |

→ For equivalent function bulk, the asm form is **~7× faster and ~7× less
memory** for golangci-lint, and ~8× faster to build. golangci only type-checks
the stub signatures, so its cost scales with the *number of functions*, not the
size of their bodies.

## Viability for the real runtime — the hard parts, tested

Two properties of the wasm2go runtime would break a naive asm port; both were
tested and **work** with the right directives:

1. **Deep recursion / stack growth.** wasm calls nest deeply. A hand-written
   `TEXT …, NOSPLIT, $0` frame cannot grow the goroutine stack and crashes. A
   growable frame that calls other Go functions first failed with
   `fatal error: missing stackmap`. **Fix (measured working):** declare a real
   frame size and add `#include "funcdata.h"` + `NO_LOCAL_POINTERS`; recursion to
   1,000,000 levels then runs correctly, including `CALL` back into Go.
2. **Calling back into Go** (the `m.T0[idx].(func(...))(...)` indirect dispatch
   and 33k `//go:linkname` cross-package calls). A `CALL ·GoFunc(SB)` from asm
   into Go works and was verified in the recursion test.

### Remaining real costs / caveats (not blockers, but real work)
* **Per-architecture.** Plan 9 asm is architecture-specific. The runtime would
  need `body_amd64.s`, `body_arm64.s`, … (the platforms go-googlesql supports),
  each generated by the wasm2go translator, plus a portable pure-Go fallback for
  any unsupported GOARCH (so `go build` still works everywhere). That fallback,
  if compiled, brings back the cost — but it can be guarded behind a build tag so
  the asm path is the default on common arches.
* **Pointer safety in frames.** The wasm runtime keeps everything in a `[]byte`
  linear memory and passes an `*base.Module`; locals are integers. As long as asm
  frames hold no live Go pointers across calls (true here — temps are i32/i64),
  `NO_LOCAL_POINTERS` is correct. Arguments that are pointers (the `*Module`
  receiver) are described by the Go stub's signature, so the runtime gets their
  stackmap from the stub. This needs care but is mechanical.
* **Generator complexity.** wasm2go already lowers WASM to a register/SSA-ish IR
  (the `vN` temps). Emitting Plan 9 asm instead of Go is a different backend, but
  the IR → asm mapping is arguably *more* natural than IR → structured Go
  (no need to reconstruct `if/goto`/labels into Go control flow). It is, however,
  a substantial new backend in the generator.
* **Debuggability / portability** of the artifact drops (asm vs readable Go), and
  it can no longer be `go vet`'d for real bugs — which is the point, but also
  means correctness rests entirely on the generator.

## Conclusion

Converting the translated function bodies to Plan 9 asm (Go stub signatures +
per-arch `.s`) is the **only approach measured so far that dramatically cuts the
golangci-lint cost at its root** (~7× wall and memory in a like-for-like test),
because the linter never type-checks the bodies. The hard runtime requirements
(stack growth, Go callbacks) are solvable with standard asm directives
(`funcdata.h`, `NO_LOCAL_POINTERS`, growable frames), verified here. The price is
a new per-architecture asm backend in the wasm2go generator plus a pure-Go
fallback for unsupported arches.

This is the highest-leverage direction found; recommend prototyping a real
wasm2go asm backend on one package (e.g. p0) end-to-end and re-measuring against
the live test suite before committing to it.
